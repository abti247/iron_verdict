# Architecture

Iron Verdict is a single-process FastAPI + Uvicorn application serving real-time powerlifting competition judging. The runtime is one Python process, one event loop. There is no horizontal scaling today — all state lives in memory.

## Runtime shape

- One Uvicorn worker. `run.py` does not pass `workers=`.
- Async I/O concurrency on a single CPU. Suitable for hundreds to low thousands of concurrent sessions, bounded by memory and message rate, not CPU.
- All state managers and broadcast lists are local to the process.

*Why single-worker:* all session state and the WebSocket registry live in process memory. A second worker would have a disjoint view of sessions and connections, so broadcasts and reconnects would silently fail across workers. Horizontal scaling requires moving state to Redis first (see [Known scale flags](#known-scale-flags)).

## HTTP surface

Served by FastAPI directly:

- `GET /` — landing page (static HTML + Alpine.js).
- `GET /vportal` — alternate landing page for VPortal-integrated sessions; serves the identical HTML as `/`. The client infers session kind from `location.pathname` at create time. No server-side marker.
- `GET /health` — single endpoint used by Railway (only during a deploy) and by the external uptime check (see *Observability*). Currently conflates liveness + readiness.  
*Why one endpoint:* Railway consumes a single health URL; splitting earned nothing on this platform. Cost: on ECS/K8s, a slow snapshot save could trip a "not ready" signal and cause an unnecessary restart loop — those platforms want `/livez` (is the process up?) separated from `/readyz` (can it serve traffic?).
- `GET /metrics` — Prometheus text format for Grafana Cloud, which scrapes it once a minute with `Authorization: Bearer <METRICS_TOKEN>` (see [Observability](#observability)). A missing or wrong token answers 401 with `WWW-Authenticate: Bearer` (compared with `secrets.compare_digest`); without `METRICS_TOKEN` the endpoint is off (404 like an unknown path) and startup logs `metrics_disabled` (`metrics_enabled` otherwise) — the app starts either way. Rate-limited per client IP, `RATE_LIMIT_METRICS` (default `30/minute`).  
*Why 401, not 404:* Grafana's Metrics Endpoint first asks without credentials and sends the token only after a 401 challenge; a 404 (the first design, to keep the endpoint unadvertised) made it give up (#185). The 256-bit token, not a hidden path, protects the data. The rate limit runs before the token check, so a 31st request within a minute gets 429 — accepted, nothing is exposed. *Why optional, unlike `ALLOWED_ORIGIN`:* a missing token only loses monitoring, never opens a hole.
- `POST /api/sessions` — create a session. Accepts optional `kind: "generic" | "vportal"` (default `generic`); rejects other values with 422. Rate-limited per client IP via slowapi (see *Client IP* below), `RATE_LIMIT_SESSION_CREATE` (default `10/hour`).
- `GET /api/sessions/{code}` — look up an active session. Returns `{"exists": true, "kind": ..., "staging_available": ...}` on 200 or 404 with `{"detail": "Session not found"}`. Path pattern `^[A-Z0-9]{8}$` rejects malformed codes with 422 before touching the session map. Rate-limited per client IP via slowapi, `RATE_LIMIT_SESSION_LOOKUP` (default `30/minute`). Both limits are logged at startup (`rate_limits_configured`); an invalid value refuses startup. *Why configurable:* Railway staging runs the E2E subset from one runner IP and cannot reset the limiter from outside, so it raises them only as far as a run and a re-run need (`60/hour`, `120/minute`; staging is public and has no Cloudflare in front); production keeps the defaults. Deliberately not tied to `TEST_MODE`, which must never be set on a deployment.  
*Why a separate endpoint instead of validating at WebSocket join:* fail-fast UX. Without it, a typo gets the user as far as the role-selection screen before failing — at a live competition that's a real cost.  
*Why the lookup also returns `kind`:* it is the single source of truth for "should the VPortal connect button appear on Select Role?" Reading from the server avoids relying on `location.pathname` (which the back-nav code scrubs to `/` via `replaceState` on every load) and lets a device that joined via QR (plain `/`) still see the connect button when the underlying session was created via `/vportal`. *Why no session name in the response:* minimizes information disclosure; the kind + existence is all callers need. *Why the kind is also kept in `iv_session` (#175):* a reloaded judge never looks the session up and a reloaded display only once its lookup succeeds, so without it role-select would hide the VPortal button while the venue network is flaky; the server's answer still overwrites the stored kind (lookup, display start).
- `POST /api/vportal/login` — proxy endpoint; forwards browser credentials to a federation's VPortal instance via a host-allowlisted outbound request and returns the JWT plus the server-clamped polling interval. See *VPortal integration* below.
- `POST /api/vportal/graphql` — proxy endpoint; forwards GraphQL reads to VPortal with `Authorization: Bearer <jwt>`. Read-only by construction: mutations and any operation outside a hard-coded allowlist of four read queries are rejected with 400 before the outbound call.
- `GET /static/*` — static assets (CSS, JS, fonts, vendored libraries) served by FastAPI. Every response carries `Cache-Control: no-cache` (same as `/` and `/vportal`): the browser keeps the file but revalidates it with `If-None-Match` before each use, and an unchanged file comes back as `304` without a body. In an AWS deployment these would move to CloudFront → S3.  
*Why no-cache, not content-hashed names with `immutable`:* without `Cache-Control` browsers reuse a file heuristically (typically 10 % of its age) without asking, so after a deploy a device that had the app open ran new HTML with old JavaScript — once stuck at "Loading …" because the old `init.js` loaded Alpine from a CDN the new CSP blocks (#135). Hashed names are the usual fix but need a build step; the ES modules import each other by fixed paths and the app has none. Cost: one short conditional request per file and page load, and no page load from cache while the server is unreachable — nothing works without it anyway. One rule for everything, vendored files and fonts included: long caching of a few small files would gain little.  
*Why Cloudflare must pass the header through:* on production Cloudflare sits in front (see *Edge*). After the v0.3.0 deploy the page stayed black: Cloudflare served v0.2.1 JavaScript it had stored before (no `Cache-Control` yet) with the new HTML (#145). Two things keep a release from needing a cache purge:
  - The origin's `no-cache` makes Cloudflare's own cache revalidate with the origin before each use (`cf-cache-status: REVALIDATED`/`MISS`). The entries stored under v0.2.1 had to be purged once.
  - Browser Cache TTL *Respect Existing Headers* passes `no-cache` on to the browser. With the default (4 h) Cloudflare sent v0.3.0's `app.js` (revalidated, origin `no-cache`) to the browser as `max-age=14400`, so a device could again mix new HTML with old JavaScript for up to 4 h after a release.

Security:

- Standard hardening headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, HSTS.
- CSP: scripts, styles and fonts only from `'self'` (plus the Umami analytics host for its script and beacon, and `api.web3forms.com` for the contact form). It allows `'unsafe-inline'` and `'unsafe-eval'` — Alpine compiles `x-show`/`x-bind` expressions at runtime via `eval`; the framework will not function without it. XSS posture is recovered structurally: the app never renders user input as HTML. The only user-controllable string written to the DOM is the session name, which is set via `x-text` (text node, not HTML).
- WebSocket origin check via `ALLOWED_ORIGIN`. **There is no in-code default:** startup (`lifespan` → `require_allowed_origin`) logs `allowed_origin_missing` at `ERROR` and aborts if the variable is unset or empty, and `run.py` then exits with code 3 so the platform marks the deploy as failed. Otherwise the resolved value is logged as `allowed_origin_configured`. Production sets `ALLOWED_ORIGIN=https://iron-verdict.com` (Railway env var), so the live deployment rejects cross-origin WebSocket handshakes; local/LAN use sets `*` explicitly (`docker-compose.yml`, `.env.example`).  
*Why the origin check matters:* Same-Origin Policy does not apply to WebSockets — without a server-side `Origin` check, any site could open a WS to `/ws` from a victim's browser and hijack the session (Cross-Site WebSocket Hijacking).  
*Why refuse to start instead of defaulting to `"*"`:* secure by default ([#60](https://github.com/abti247/iron_verdict/issues/60)) — a new deployment (staging, fork, typo in the variable name) that forgot the variable used to accept any origin silently. *Why an explicit `"*"` and no `ENVIRONMENT` flag:* LAN hosting at a venue legitimately needs `*` (judges open the laptop's LAN IP); one variable whose absence is the only error is simpler than a second flag whose own default could reopen the gap.

## WebSocket surface

`GET /ws` is the single WebSocket endpoint. Message types after `join`:

- `vote_lock` — judge locks a colour (and optional reason), tagged with the `lift_id` it was cast for. Always answered to the voter with exactly one of:
  - `vote_ack` `{color, reason, lift_id}` — the vote is stored. A duplicate `vote_lock` (judge already locked) is also acked, carrying the **stored** vote: resends are idempotent and the server's vote is what the judge sees.
  - `vote_rejected` `{code, message}` (logged as `vote_rejected`) — `code` is `lift_changed` (the `lift_id` is stale), `reason_required` (reasons are mandatory and none was given) or `invalid` (bad colour/reason/lift id, or not a judge). Nothing is stored. `SessionManager.lock_vote` checks the lift before the mandatory reason, and the already-locked case before both. Why: a stale vote must always surface as `lift_changed` — answering `reason_required` would let the judge add a reason and turn the previous lift's colour into a vote for the new lift.
- `settings_update` — head judge changes lift type, show-explanations, require-reasons.
- `timer_start`, `timer_reset` — head judge controls the 60-second attempt timer.
- `next_lift` — head judge resets state for the next attempt; broadcasts `reset_for_next_lift` with the new `lift_id`.
- `end_session_confirmed` — head judge ends the session.
- `pause_start` `{minutes}` or `{end_at_ms}` (a time of day converted by the display), plus optional `next_lift`; `pause_end` — a **display** starts (or replaces) or ends the session's pause (#163). Answered with a broadcast `pause_update` `{pause, server_now_ms}` (`pause`: `{end_at_ms, mode, next_lift}` or `null`; `pause_end` broadcasts even when no pause ran, so the sender always gets an answer), or to the sender only with `pause_rejected` `{code}`: `past`, `too_long` (> 12 h) or `invalid`. Judges get `error`. See *Pause*.
- `pong` — client reply to server-initiated heartbeat ping.

A second `join` on a socket that already joined is answered with `error` "Already joined" (logged as `second_join_rejected`); the first role stays registered. *Why:* the client sends one `join` per socket; registering one socket under two roles left an orphaned entry once it closed ([#136](https://github.com/abti247/iron_verdict/issues/136)).

Head-judge-only messages (`timer_start`, `timer_reset`, `next_lift`, `end_session_confirmed`, `settings_update`) from any other role get an `error` and leave the session unchanged — the UI only hides these buttons, the server is the actual guard.

*Why `vote_ack` / `vote_rejected` instead of fire-and-forget:* the client's socket can look open while the network is gone, and `websocket.js` drops sends on a closed socket. Without an explicit answer the judge screen cannot know whether a vote counted; showing "Vote Locked" optimistically let a lost vote hang the competition with nobody seeing why. *Why `lift_id`:* a vote queued offline is resent after reconnect; if the head judge advanced meanwhile, the server would otherwise count it for the wrong lift. `lift_id` is optional in `vote_lock` so a tab still running the previous frontend during a deploy keeps working (without the stale-lift check).

Per-connection rate limit: 20 messages/second via a sliding window. Exceeding it closes the connection with code 1008. Per-IP concurrent-connection cap is delegated to the edge (Cloudflare).

Global connection cap `MAX_WEBSOCKETS` (default 2000): a `join` while `ConnectionManager.count_connections()` (joined sockets across all sessions) is at the cap gets `join_error` "Server at capacity", is logged as `websocket_cap_reached` and closed with code 1013 (try again later); the client shows "Failed to join session" and does not retry. Checked **before** `join_session`, so a rejected judge is never marked connected. A judge presenting its valid reconnect token is exempt — it only replaces its own connection, which may still be counted (half-open, or not yet released). Sockets that never sent `join` are not counted. The check is not atomic with the registration: concurrent joins can pass it together and exceed the cap by a few. *Why:* backstop if the edge misses a flood or a deployment runs without Cloudflare (local Wi-Fi); costs nothing below the cap ([#61](https://github.com/abti247/iron_verdict/issues/61)).

*Why split the limits this way:* per-connection caps are cheap and local — they protect the message-handling path from a single buggy or malicious client. Per-IP concurrency caps need cross-connection awareness that the edge already has, plus Cloudflare can tie them to broader signals (bot scoring, ASN reputation) that the app process cannot.

## State management

Two in-process managers, each guarded by its own `asyncio.Lock`. The two locks are never held together.

*Why two locks instead of one:* the managers have orthogonal concerns — domain state vs. transport — and conflating them would either serialize all WebSocket I/O behind every domain mutation, or vice versa. *Why never held together:* taking two locks in any order opens a deadlock window if some future path ever inverts the order. The rule "never both" makes deadlock structurally impossible. Accepted cost: any operation that conceptually needs both must split into two phases (compute under one lock, then act under the other) — no such operation has been needed so far.

### `SessionManager`

- Holds `self.sessions: dict[str, dict]` — domain state per session code.
- Each session records: `name`, `kind` (`"generic" | "vportal"`, immutable after create), `judges` (left/center/right with vote, reason, locked, connected, reconnect token), `phase`, `state`, `settings` (`show_explanations` default on, `lift_type` default squat, `require_reasons` default off; snapshots keep their stored values), `timer_started_at`, `timer_frozen_ms`, `lift_id` (counter, +1 on every reset for next lift; `0` for snapshots that predate it), `pause` (`null` or `{id, end_at, mode, next_lift}`, `end_at` in epoch seconds; `null` for snapshots that predate it), `last_activity`.  
*Why `kind` lives in session state:* drives whether the VPortal connect button appears on Select Role and whether the display screen starts polling. Set at create, read by every consumer via `GET /api/sessions/{code}`.
- Generates 8-character alphanumeric session codes.
- Owns business rules: vote-lock state machine, all-judges-locked → results computation (including the IPF rule that a disconnected non-voter blocks results), timer freeze on results, reset for next lift, pause validation (`start_pause` / `end_pause`, see *Pause*), and a running pause keeps a session from expiring.

### `ConnectionManager`

- Holds `self.active_connections: dict[session_code, dict[role, WebSocket]]` — transport registry only.
- Tracks `_last_pong: dict[WebSocket, float]` for the heartbeat task.
- `remove_connection_if_current(code, role, ws)` removes a role only while `ws` still holds it — the identity guard (see [Reconnection model](#reconnection-model)).
- `count_connections()` counts all registered sockets for the global `MAX_WEBSOCKETS` cap (see [WebSocket surface](#websocket-surface)); `count_displays(code)` serves `DISPLAY_CAP`.
- Provides `broadcast_to_session`, `broadcast_to_others`, `send_to_role`, `send_to_displays`. Per-socket errors are swallowed and emit warning logs by name.

*Why swallow per-socket errors:* one dead or slow client must not abort the broadcast to the others. The alternative — propagating the first send failure — would let a single misbehaving client (or a TCP RST on one judge's connection) stall state propagation to the remaining judges and the display.

## Persistence

`/data/sessions.json` is a periodic JSON snapshot used **only** for crash recovery, not for state sharing between processes. Checked every 60 seconds by the lifespan task and written only if its content changed since the last write (or since the load at startup); on shutdown it is written once more, unconditionally. On Railway it is volume-backed; on ECS/Fargate it would need EFS.

*Why a JSON file and not a database:* the only requirement is "survive a Railway restart with active sessions intact." A flat file gives that with zero operational overhead — no migrations, no connection pool, no schema. Accepted cost: up to 60 s of mutations lost on crash, no point-in-time recovery, no querying. *Why not skip persistence entirely:* a deploy or OOM mid-event would wipe judges' in-flight votes; the 60 s snapshot bounds the blast radius.

A running pause is part of the snapshot; after loading it `restore_pause_timers` arms its end again (an end already passed fires at once), and a session with a running pause never expires (a pause may outlast the session timeout).

Snapshots exclude reconnect tokens — those exist only in memory and die with the process. Reconnects after a restart are not supported.

*Why exclude tokens from the snapshot:* tokens are session-scoped secrets. Persisting them widens the blast radius if `/data/sessions.json` ever leaks (volume mount misconfiguration, debug dump, leaked backup). The trade-off is intentional — after a restart, judges rejoin via the session URL and pick a free role; the friction is acceptable for a 60-second-recovery-window failure mode.

## Reconnection model

- **Judges** receive a 32-character `reconnect_token` on first join. A new WebSocket presenting the matching `(session_code, role, token)` triple replaces the existing connection. An identity guard prevents the disconnect handler of the old socket from clobbering the new one. Tokens survive `reset_for_next_lift`.
- **Releasing a connection:** `release_connection` (in `main.py`) unregisters a socket through the identity guard and, for a judge, sets `connected = False` and broadcasts `judge_status_update`. The WebSocket handler calls it in `finally` on every exit — regular disconnect, flood disconnect, unexpected exception — and the heartbeat calls it for dead connections. *Why `finally`, not only on `WebSocketDisconnect`:* any other exit left an orphaned entry that took a display slot, was pinged every 5 s forever and survived session expiry ([#136](https://github.com/abti247/iron_verdict/issues/136)).
- **Concurrent joins on one role** yield exactly one success. Single-worker asyncio is the guarantee, not a lock: `join_session` is synchronous, so its "role free?" check and the write cannot interleave. The reconnect takeover awaits (closing the old socket) between token check and slot takeover, so it re-checks the token afterwards — a second client with the same token (e.g. a duplicated browser tab copies `sessionStorage`) gets "Role already taken" once the winner has rotated the token. *Why:* otherwise both clients got `join_success` and one acted as judge without receiving broadcasts ([#57](https://github.com/abti247/iron_verdict/issues/57)). Breaks with multiple workers like all in-memory state.
- **Displays** have no reconnect token. Each display join takes the next free display slot (`display_aabb1122` random suffix). Displays are interchangeable viewers, capped per session by `DISPLAY_CAP` (default 20).
- Judge slots cap at 3 (left, center, right) and are exclusive.
- **Votes across reconnects:** the judge screen keeps an unconfirmed vote in memory and in `sessionStorage.iv_pending_vote` (memory covers a failing storage write, storage covers a reload). After every `join_success` it reconciles with the server's snapshot of that judge: server has a vote → shown as confirmed; server has none but one is pending → resent automatically (a stale `lift_id` is rejected with `lift_changed`); neither → open. A vote shown as locked locally but unknown to the server (the lift was reset while offline) reverts to open.

*Why tokens for judges but not displays:* judges have identity that must persist across reconnects — their vote, lock state, and reason are tied to a specific role. Displays are read-only viewers whose only state is "what's currently on screen", recoverable from the next broadcast. Adding tokens for displays would buy nothing and complicate slot bookkeeping for an unbounded viewer count.

*Why the identity guard:* when a judge reconnects, the new socket replaces the old one in the registry. Without the guard, the *old* socket's disconnect handler (which fires as the underlying TCP tears down) would clear the slot — disconnecting the live new socket and dropping the judge.

*Why a display cap:* every state change fans out to all displays in a session. Without a cap, a single session could become a broadcast amplifier — a malicious actor opens hundreds of display tabs, every `vote_lock` multiplies into hundreds of WebSocket sends, and CPU/bandwidth on the single worker spikes.

## Background work

Single `lifespan` task runs two periodic operations:

- **Snapshot save** — every 60 seconds, only if the serialized sessions differ from the last snapshot written (or loaded). Serialization runs in the event loop; the file write runs in a worker thread (`asyncio.to_thread`). Deleting the last session changes the content to `{}`, which is written once. The shutdown save stays synchronous and unconditional.  
*Why compare content, not a dirty flag:* sessions are mutated in many places (votes, timer, settings, connected flags); a flag would have to be set at every one of them, and a forgotten one means lost state after a restart. Serializing a few kilobytes once a minute is cheap. *Why serialize before the thread:* the thread must not read session dicts the loop mutates at the same time. *Why no timeout on the write:* a thread cannot be cancelled; during normal running a hung disk only stalls the cleanup loop, not voting or the heartbeat. A lock around the file write keeps the shutdown save from interleaving with an in-flight periodic write — on a hung disk the synchronous shutdown save then waits on that lock, as a hung synchronous write did before.
- **Cleanup expired sessions** — every 30 minutes; deletes sessions with `last_activity` older than 4 hours.
- **Pause end** — one task per session with a pause (`schedule_pause_end` in `main.py`, registry `_pause_end_tasks`): sleeps until `end_at`, then ends that pause (matched by its `id`, so a replaced pause is left alone) and broadcasts `pause_update` `null`. Re-armed on every start, cancelled on end, timer start and session end. *Why a task and not the heartbeat tick:* the end must show on time on every display; the sleep is the pause the operator chose, not an artificial delay.

A failure in either operation (e.g. `OSError` on a full or read-only volume) is logged (`snapshot_save_failed` / `session_cleanup_failed`) and the loop keeps running; a failed write leaves the last-written snapshot unchanged, so the next tick retries it.  
*Why catch per operation:* an uncaught exception would end the task silently — no further snapshots, no more expiry — and re-raise from `await task` at shutdown, skipping the heartbeat cancel and the fallback save.

A server-initiated heartbeat (`heartbeat_sweep`, every `HEARTBEAT_INTERVAL_SECONDS` = 5 s) pings every WebSocket client and closes (code 1001) any client without a `pong` for more than `PONG_STALE_SECONDS` = 15 s — effectively 15–20 s, since the check runs once per interval. The sweep removes a connection itself (via `release_connection`) right after a stale close, and when a ping cannot be sent (logged once as `heartbeat_dead_connection_removed`). *Why the heartbeat removes, not only the handler:* the handler may already have ended, so nobody else would ever clean the entry up; the identity guard keeps it from removing a newer connection of the same role. The client runs the mirror-image watchdog (see [WebSocket client](#websocket-client)).
*Why 5 s / 15 s:* a half-open connection — typical on venue Wi-Fi when a device switches access points — fires no close event on either side; with the former 30 s / 70 s a judge looked connected for over a minute while votes went nowhere. One ping per client every 5 s is negligible next to the 20 messages/s rate limit.

## VPortal integration

Optional, pull-only overlay of the current lifter on the display screen for sessions created via `/vportal`. The integration is opt-in at session creation; generic sessions are unaffected.

**Architecture.** Stateless Python proxy ([src/iron_verdict/vportal_proxy.py](../src/iron_verdict/vportal_proxy.py)) + client module ([src/iron_verdict/static/js/vportalClient.js](../src/iron_verdict/static/js/vportalClient.js)). The JWT lives in browser `localStorage` keyed by session code (`vportal:<sessionCode>`); the proxy holds no tokens, no credentials, and no per-session state — only a shared `httpx.AsyncClient` plus the host and operation allowlists.

*Why client-side storage instead of server-side sessions:* a server-side token store concentrates risk — one server-side leak compromises every active session. localStorage scopes the blast radius to a single device; the existing XSS surface is small (no user-generated content rendered to HTML, Alpine `x-text` only). Accepted cost: standard browser threat model — XSS would steal the token.

**Data flow per polling cycle.** Browser reads `{host, token, competition_id, stage_id}` from localStorage; the proxy forwards two GraphQL reads per tick (`competitionGroupList`, then `competitionAthleteAttemptList`) with `Authorization: Bearer <token>`. `profile.competition.id` is fetched once at login and cached. Polling cadence is server-controlled via `VPORTAL_FETCH_INTERVAL_MS` (default 3000ms, clamped to 2000ms minimum); the client receives the clamped value at login and uses it — no client-side default.  
*Why server-controlled with a hard minimum:* prevents a malicious or buggy client from polling sub-2000ms, and keeps tuning a between-event operation (Railway env var → redeploy) rather than a code change.

**Security boundaries.**

- **Host allowlist** in the proxy: `bvdk.vportal-online.de`, `oevk.vportal-online.de`, `staging-bvdk.vportal-online.de`, `staging-oevk.vportal-online.de`. When `TEST_MODE=1`, `localhost`/`127.0.0.1` (and `host:port` variants) are additionally allowed for the E2E fake-server fixture. Any other host returns 400 before the outbound call — the proxy is not an open relay.
- **GraphQL operation allowlist**: hard-coded set of four read operations (`profile`, `competitionStageList`, `competitionGroupList`, `competitionAthleteAttemptList`). Mutations and any other top-level field are rejected with 400. Iron Verdict therefore cannot write to VPortal even if a modified client tries — the official scorekeeper continues to record verdicts on the VPortal side manually.  
*Why an allowlist instead of trusting "we only send reads":* defence in depth. A leaked or stolen JWT grants whatever permissions the operator account has; without the gate, a malicious client could send mutations through the same proxy that's already authenticated. The four-operation allowlist makes write attempts a 400 at our edge.
- **No credential storage server-side**. Login credentials cross the proxy in-memory for the duration of one request and are not logged. The JWT flows back to the browser.

**Failure isolation.** Every VPortal failure path — wrong credentials, expired token, upstream 5xx, unreachable network, empty active group, missing stage — leaves the core judging functionality (lights, timer, votes, verdict, WebSocket layer) fully operational. The overlay is strictly additive: corners hide, an unobtrusive banner may appear, and the rest of the display continues to render.

**Display overlay lifecycle.** On a display join `startDisplayOverlay()` reads the session kind from `GET /api/sessions/{code}` and starts the poller only for `kind=vportal` on a device that has its own VPortal login with a stage. If that lookup fails (network error or non-2xx) on such a device, the disconnected banner shows and the lookup is retried at the polling interval until it succeeds; a device without its own login looks up once and never polls. Leaving the display (role-select, landing, session end) calls `stopDisplayOverlay()`, which stops the poller and any pending retry and clears the overlay; every start begins with the same stop, so a display never runs two pollers. A run counter keeps a lookup or poll that was still in flight when the display was left from starting a poller or writing the overlay. A final `join_error` stops the overlay as well. On the display, a connect or disconnect in the VPortal dialog (the stream overlay's panel) restarts it with the new login.  
**Connect button after a reload (#172).** The button and dialog show the login stored on the device (`vportal:<code>` with a stage) as connected, with "Disconnect" — on role-select and in the stream overlay's panel. `showStoredLogin(code)` sets `connected` from storage whenever the page enters a session: create (`loadStagingFlag`), lookup (`applySessionInfo`), reload recovery (with the stored kind, #175) and display start (a reloaded display never runs the lookup; called before the display's session lookup so a failed one cannot leave a previous session's state). A login without a stage or with a token known to be expired counts as not connected; a token that VPortal rejects shows only at the first poll, as the disconnected banner.  
*Why from storage on every session entry:* the stored login is the real state (it keeps the display polling), so the button must show it after a reload; and since storage is keyed by session code, setting the state on each entry means a tab that switches session never shows the previous session's login.  
*Why retry the lookup:* a display is typically reloaded exactly when the venue network is bad; the WebSocket reconnects on its own, and before #112 the lifter data then stayed missing without any hint until another reload. *Why the existing banner and not a new message:* to the person at the display the effect is the same as a lost VPortal connection — lifter data missing — and it clears itself once polling works.

**Upstream errors on `/login`.** Every upstream failure of the login flow returns **424** with `detail: {"reason": <code>}` — `no_session_cookie` (`/account/login` set no `__Host-VPORTAL`/`VPORTAL` cookie), `token_exchange_failed` (`/auth/token` answered neither 200 nor 302/401/403; `upstream_status` added to `detail`), `missing_access_token` (200 without an `access_token` in a JSON object), `unreachable` (transport error on either request, no retry). Wrong credentials (302/401/403 from `/auth/token`) stay 401 and write a `vportal_login_rejected` **info** log with the same status/header/cookie-name fields — a missing role may look like a wrong password to us, and the redirect target tells them apart. Each 424 writes one `vportal_login_failed` warning with `reason`, `host`, the status and `Location` of `/account/login` and `/auth/token`, the token response's `content_type`, the **names** of the cookies `/account/login` set, and for `unreachable` the `upstream_path` and `error` class — never cookie values, credentials or bodies. The connect dialog maps the reason to a translated message (`static/js/vportalErrors.js`); unknown reasons and other statuses get a generic message with the HTTP status.  
*Why 424 instead of 502:* Cloudflare replaces the body of an origin 502 with its own "Bad gateway" page, so the reason never reached the dialog or the browser's network tab (staging login, 2026-10-13, issue #100). A non-5xx status passes through unchanged. `/graphql` keeps 502 — the polling client only counts failures there.

**Upstream errors on `/graphql`.** The proxy maps VPortal failures to explicit statuses so an upstream problem never looks like an Iron Verdict bug (500): 401 → 401 (`token-expired` in the client); 5xx → 502 "VPortal upstream error"; a transport error (connection closed without response, connect error, timeout, reset) is retried **once**, immediately (logged as `vportal_transport_retry` at info level with `host` and `error` class), and only a second failure returns 502 "VPortal upstream unreachable" plus a `vportal_upstream_unreachable` warning log (`host`, `error` class). Any other response whose body is not JSON (e.g. an HTML maintenance or web-firewall page with 200, a 3xx with empty body — httpx does not follow redirects) returns 502 "VPortal upstream invalid response" plus a `vportal_upstream_invalid_response` warning log (`host`, `upstream_status`, `content_type` — never body or token). Other statuses with a JSON body (3xx/4xx except 401) are passed through as 200 unchanged; the client does not read GraphQL `errors`. HTTP error responses and invalid bodies are never retried. The login path has no retry.  
*Why retry transport errors:* the shared `httpx.AsyncClient` pools keep-alive connections; VPortal or a NAT/load balancer can close an idle one just before the next poll reuses it (seen live 2026-05-23 as a single `RemoteProtocolError` between successful polls). httpx discards the dead connection, so the retry runs on a fresh one and the display never notices. Safe because the operation allowlist makes every forwarded call a read. *Why no delay before the retry:* the cause is a stale connection, not an overloaded upstream. *Why log the retry although it usually succeeds:* the stale-connection explanation rests on one observed incident; the retry log shows in the field how often and when it happens, and whether the error class fits. Accepted cost: if VPortal hangs, a request takes up to two client timeouts (2 × 5 s) before the 502.

## Observability

Grafana Cloud (free tier, EU) pulls everything; the app opens no outbound connection for monitoring, so a Grafana outage cannot affect a competition. Setup, alert rules and the weekly review: [docs/monitoring.md](monitoring.md).

- **Uptime from outside:** Grafana Cloud (free tier, region EU) Synthetic Monitoring calls `https://iron-verdict.com/health` every minute from 2 EU locations and expects 200 with `"status":"ok"`. When both locations fail in 2 consecutive minutes, an alert rule with `severity=critical` sends "PROD nicht erreichbar" to the maintainer's phone via Telegram, and a resolved message once it is green again. If the check stops delivering data or the query fails, the same route sends a `DatasourceNoData`/`DatasourceError` alert (monitoring broken, not PROD down). Only `severity=critical` is delivered; everything else is muted and reviewed in the dashboard. No e-mail delivery. Setup and test alert: [docs/monitoring.md](monitoring.md).
- **Railway checks `/health` only during a deploy** (it decides whether the new deployment goes live), never afterwards. A process that hangs or dies later is only caught by the external check.
- **Logs:** JSON lines on stdout (`logging_config.py`, whitelisted fields only), read in Railway.
- **Metrics:** `GET /metrics` (`metrics.py`, `prometheus_client`, own `CollectorRegistry`):
  - Counted on scrape by `LiveStateCollector` from `SessionManager` / `ConnectionManager`: `iron_verdict_sessions_active{kind}`, `iron_verdict_judges_connected`, `iron_verdict_displays_connected`.
  - Counters at the code path: `iron_verdict_votes_total` (stored votes; idempotent resends not counted), `iron_verdict_votes_rejected_total{code}`, `iron_verdict_ws_disconnects_total{reason}` (`client`, `heartbeat_stale`, `heartbeat_send_failed`, `flood`, `replaced` — a token reconnect took over a still registered socket, `error` — the handler raised; a session ended by the head judge is not a disconnect; counted where the socket is released, so each loss once — except `flood`, which is also counted for a socket that never joined, as an abuse signal), `iron_verdict_snapshot_failures_total`, `iron_verdict_unhandled_exceptions_total` (HTTP handler and WebSocket handler), `iron_verdict_http_requests_total{status_class}` (pure ASGI middleware; an unhandled exception counts as `5xx`; WebSockets are not counted).
  - `iron_verdict_snapshot_last_ok_timestamp_seconds` — set after every successful `save_snapshot_if_changed`, also when nothing changed and nothing was written.
  - `iron_verdict_build_info{version}` and the process metrics (`process_resident_memory_bytes`, CPU, open files).

*Why counted on scrape for sessions and connections:* same reason as "compare content, not a dirty flag" for the snapshot — a forgotten join or leave path cannot make the number wrong. *Why `snapshot_last_ok` also without a write:* otherwise the "snapshot too old" alert would fire in every quiet phase. *Why only totals as labels:* no session codes, names, IPs or paths — for privacy, and because every label value is its own time series (free tier: 10,000). *Why an own registry:* the default registry would also collect whatever imported libraries register and rejects a second registration when a test reloads a module. *Why pull, not push:* nothing in the critical path waits on Grafana.

*Why from outside, through `iron-verdict.com`:* the check takes the judges' path (DNS, Cloudflare, TLS, app), so an outage of any of them alerts, not only of the process. Production has no Railway domain that bypasses Cloudflare (see *Edge*). *Why only critical alerts:* the maintainer is at the venue during competitions and must be able to act on every message (rollback, switch the organiser to the laptop fallback); a phone that also buzzes for warnings gets ignored. *Accepted cost:* the uptime check sees only reachability of `/health` — voting, connections and snapshots come from the metrics below; logs follow in #134.

## Edge

- Cloudflare proxy (orange cloud) sits in front of Railway. SSL/TLS Full (strict), Bot Fight Mode on.
- Caching → Browser Cache TTL: **Respect Existing Headers** (set 2026-10-18, #145), so the origin's `Cache-Control: no-cache` reaches the browser (see `GET /static/*`).
- Domain: `iron-verdict.com` → CNAME → Railway.
- **Client IP:** rate limits and every `client_ip` log field (HTTP and WebSocket) use `CF-Connecting-IP`, falling back to the TCP peer (`request.client.host`) when the header is absent. `X-Forwarded-For` is ignored.  
*Why:* in production the TCP peer is Railway's edge proxy — an address from `100.64.0.0/10` that varies even for one client (seen in the PROD log, #124) — so counting it limited neither per client nor reliably globally. Cloudflare sets `CF-Connecting-IP` itself and overwrites a client-sent value; the first `X-Forwarded-For` entry is whatever the client sends. Production has no Railway domain that bypasses Cloudflare. *Accepted cost:* staging has no Cloudflare in front, so a client there can choose its own `CF-Connecting-IP` and sidestep the limits; staging only carries test sessions. Several competitions in one hall behind one public IP share the limits.

## Build and deployment

- One Docker image (`Dockerfile`, Python 3.13 slim). The entrypoint chowns `/data` (Railway mounts volumes as root) and drops to `appuser` via `gosu`. `APP_VERSION` is baked in at build time as `sha-<commit>` and shown in the landing-page footer.
- CI builds the image on every PR and smoke-tests the running container ([.github/workflows/image.yml](../.github/workflows/image.yml)). Commits on `main` that pass CI and the image check are pushed to `ghcr.io/abti247/iron_verdict` as `sha-<commit>` and `main`; a `vX.Y.Z` Git tag re-tags that same image without rebuilding and creates the GitHub release.
- Railway project with two environments of the same service:
  - **production** (`iron-verdict.com`, behind Cloudflare) runs a release tag `vX.Y.Z`. Deploy and rollback are a manual change of the tag in the Railway service settings.
  - **staging** (`ironverdict-staging.up.railway.app`, Railway subdomain, no Cloudflare) runs permanently with its own `/data` volume and the production variables, except `ALLOWED_ORIGIN` (its own domain) and the raised rate limits. Only the release chain changes its image.
- Release chain (`main.yml`), only for a commit whose `pyproject.toml` version has no tag yet: approval **Release-Kandidat** → `scripts/railway_deploy.sh` points staging at `sha-<commit>` via Railway's GraphQL API (project token limited to the staging environment, GitHub secret only in that environment) and waits until Railway reports the deployment successful and the footer shows that version → `remote_safe` E2E against staging → approval **Release** → `release.yml` tags `vX.Y.Z`, re-tags the image and creates the GitHub release. Pushed tags start nothing. Runbook: [docs/release.md](release.md).

*Why build once, promote:* what runs at a competition is bit-identical to what was tested, and a rollback is a tag change (about a minute) instead of a local rebuild. *Why staging before the tag:* the PR and image checks run on GitHub runners; Railway's proxy/TLS, the public-domain WebSocket, variables and volume are only tested there. Tagging last means no version tag ever points at a commit that failed staging.

## Frontend

No-build single-page application. One HTML file served by FastAPI's `StaticFiles`; JS loaded as native ES modules via `<script type="module">`. No bundler, no transpilation, no node_modules.

*Why no build step:* the app is small enough that a bundler earns nothing — no tree-shaking pay-off, no code-splitting need, no TypeScript surface to compile. The dev loop is "edit file → refresh"; CI does not need a frontend build stage; the Docker image carries no `node_modules`. Accepted cost: no minification (file sizes are already small, Cloudflare brotli-compresses on the wire), no TS, and any future move to a framework with required tooling (React, Svelte) would need to introduce the toolchain. The Vitest test runner *does* pull in `node_modules`, but only as a devDependency — it never ships to production.

**Vendored dependencies (served same-origin, no CDN):**

- `static/vendor/alpinejs-3.14.1.min.js` — Alpine.js (CDN build, auto-starts on load; `init.js` injects it).
- `static/vendor/qrcodejs-1.0.0.min.js` — QRCode.js, QR code on the role-select screen.
- `static/fonts/` + `static/css/fonts.css` — Bebas Neue and Rajdhani (400/600/700) as woff2, the same `unicode-range` subsets Google Fonts serves (latin, latin-ext, devanagari); the browser only downloads a subset a page actually uses. `font-display: swap`.
- License files sit next to the files (`vendor/LICENSE-*`, MIT; `fonts/OFL-*.txt`, SIL OFL 1.1). Upgrading a library means replacing the file and its versioned name in `index.html` / `init.js`.

*Why vendored:* everything after a judge or display opens the page is critical path, and venue Wi-Fi may have no or very slow internet. With Alpine on a CDN the page stayed invisible (`x-cloak`) when the CDN was unreachable; with Google Fonts a slow connection held up the start until the request timed out. `init.js` still waits for the four font faces before injecting Alpine, so the first render is in the right font — served locally, that wait is milliseconds. `test_offline_assets.py` runs a full competition with every foreign host blocked.

**Guide images:** `static/img/guide/{de,en}/*.webp` — screenshots of the chief referee's phone picking a reason and of the display (result with reasons, layout editor), shown in the demo guide in the current language, one set per language, served same-origin like every other static file. They are generated by `scripts/guide_screenshots.py` and committed (see `docs/testing.md`, Guide screenshots).  
*Why committed, not built:* the Docker build would need Playwright and Chromium; generated in a PR, the images are reviewed like any other change.

**Boot sequence:** `<html class="booting">` is in the markup. `boot.css` hides every top-level element of `<body>` except `.boot-screen` (spinner, "Laden … / Loading …") while that class is set. `init.js` loads the locales and fonts, injects Alpine, and removes `booting` on `alpine:initialized`, so the first screen Alpine renders replaces the indicator in one step. On a reload with a stored session that first screen is the *reconnecting* screen (see *Screen machine*), never the landing screen. If Alpine has not started after 10 s, a CSS animation delay swaps the indicator for a bilingual "could not be loaded" message with a reload link (`<a href="">`, keeps the query string); if the Alpine download fails, `init.js` sets `boot-failed` and the message shows at once. The boot screen is plain markup without Alpine or i18n.

*Why a global boot state instead of `x-cloak` alone:* every new top-level element had to remember `x-cloak`; the VPortal modal did not and flashed up as a full-screen login dialog until Alpine started. The boot state hides everything regardless (`x-cloak` stays as well). *Why the fallback is pure CSS:* it also appears when no JS runs at all (e.g. `init.js` fails), where a JS timer would never fire — a silent black screen becomes an understandable message.

- Umami Analytics — cookieless, no personal data; loaded with `defer`, nothing waits for it.
- web3forms — contact form submission only.

### Screen machine

`Alpine.store('nav').screen` drives which screen is shown (`x-if` or `x-show`, see *JS modules*). The URL stays at `/`; only `history.state` changes:

```
(reload) reconnecting → judge / display / role-select   (failure or Cancel → landing)
judge / reconnecting → role-select with notice           (position taken by another device, see roleTakeover.js)
landing → role-select → judge
                     → display
demo-intro → (opens 4 pop-up windows)
contact / privacy  (info-only screens)
(?session=…&overlay=1) display                           (stream overlay: never leaves it, see *Stream overlay*)
```

Real screen transitions go through `$store.nav.navigateTo(screen)`, which sets `screen` and pushes `{screen}` onto the browser history. `navigateTo` is idempotent — repeated transitions to the same screen (notably from `handleJoinSuccess` on every WebSocket reconnect) don't pollute the back-stack with duplicates. `app.js` seeds the stack with `replaceState({screen: 'landing'})`. The `popstate` listener in `init.js` passes `event.state.screen` to the connection's `followHistory()`, which dispatches to `returnToRoleSelection()` / `returnToLanding()` (which clear vote state and close the WebSocket) or sets `screen` directly for info-only targets; a `handlingPopstate` guard prevents the helper from re-pushing state during back-navigation. **Why:** before this, the browser back button exited the app — now it steps through screens (judge → role-select → landing) and properly tears down the live WebSocket on the way.

Reload behaviour follows the same model. `iv_session` is upgraded as the user moves forward — `{code}` once a code is created or validated, `{code, role, reconnect_token}` once a role is picked; a VPortal session also stores `kind: 'vportal'`, restored on reload (see *Why the kind is also kept in `iv_session`*). On reload the connection's `start()` reads `iv_session` and, if it holds a code, sets `screen = 'reconnecting'` before Alpine's first render ("Connecting to session <code>", spinner, Cancel): full state rejoins the judge/display right away (the WebSocket retries as usual while the server is unreachable — the page stays on *reconnecting*); code-only state re-validates against `/api/sessions/{code}` and returns to role-select. `join_success` (or the successful lookup) replaces *reconnecting* with the real screen. A stale code (session ended or expired between reloads — `join_error` "Session not found" or a 404 lookup) clears `iv_session` and shows landing with an inline "Session <code> has ended or expired" message; other join errors keep their popup and then go to landing; a failed lookup (network) shows landing with the "Couldn't verify session" error and the code pre-filled. Cancel behaves like leaving the session (`returnToLanding()`: closes the socket, clears `iv_session`); a session lookup that answers after Cancel is ignored. **Why** a dedicated screen: a judge who reloads mid-attempt must not see the landing screen and think they were thrown out. **Why** no delay before the rejoin: `start()` runs on `alpine:init` against the already registered stores and the screen only changes on the server's answer, so the former 100 ms `setTimeout` protected nothing. Demo windows (`?code=…&demo=…`) still join after their own 100 ms delay and are not affected.

*Why rehydration uses `replaceState`, not `pushState`:* a one-shot `navigateInPlaceNext` flag tells the next `navigateTo` to replace the current entry instead of pushing. The post-reload back-stack therefore matches the pre-reload one exactly — same depth, same prior entries — so the existing role-select entry (or whatever was below judge before the reload) is what swipe-back returns to. Without this, mobile in-app browsers (e.g. iOS Safari opened from a QR scanner) skip JS-pushed history made after the reload and the swipe-back gesture exits the launching app instead of stepping back within iron-verdict.

QR entry point: `?session=XXXX` lands on the landing screen with the code pre-filled, immediately triggers the lookup validator, and navigates to role-select only if the code resolves to an active session. Invalid or unknown codes surface an inline error on landing. The init-time `replaceState` cleans the URL on entry regardless of outcome. **Why** URL params are captured before the replaceState: scrubbing the query string clears `window.location.search`, so the QR code must be read first.

### WebSocket client

`websocket.js` wraps the native `WebSocket` with:

- Reconnect waits 0.5 s → 1 s → 2 s → 3 s max, each ±20 % jitter; resets to 0.5 s on successful open.
  *Why so short instead of classic exponential backoff:* backoff protects servers with thousands of clients from a reconnect storm; a session has ~5 clients, so the trade-off favours recovery — with the old 16 s cap a judge could stay offline up to 16 s after the server was back (e.g. after a deploy). The jitter still keeps clients from hitting a restarted server in the same instant.
- Immediate reconnect while waiting for a retry: `online` (device back on the network), `visibilitychange` to visible (tab back in front) and `pageshow` with `event.persisted` (bfcache restore) cancel the pending retry timer and connect at once. An open socket or an attempt in progress is left alone, so these never create a second socket (an open-but-dead socket is the watchdog's job). If the socket is `CLOSED` without its close event having reached the wrapper (page frozen in the bfcache), it is abandoned like a watchdog drop and replaced. The listeners are removed on `close()`.
  *Why in the wrapper, not in the app:* the earlier bfcache handler in `app.js` called `joinSession()` again, creating a second wrapper while the first one's retry timer could still fire — two sockets for one judge. One wrapper owning every reconnect trigger keeps exactly one active socket.
- `stopped` flag prevents reconnect after intentional close (e.g. "Back to Landing").
- Heartbeat watchdog (judges and displays alike): if no server message of any kind arrives for 15 s (3 missed pings), the wrapper abandons the socket — handlers detached, `close()` called — reports it as dropped (indicator turns "reconnecting") and connects a new socket immediately. Checked every 2.5 s, so detection takes 15–17.5 s. A gap of more than 5 s between two checks means the browser paused or throttled timers (background tab, frozen page); the watchdog then restarts its count instead of reconnecting, since incoming messages may still be queued behind the pause.
  *Why detach handlers instead of waiting for `onclose`:* on a half-open connection the close handshake can hang for a long time; the old socket's late `onclose` or messages must not trigger a second reconnect or reach the app. *Why only on the open socket:* a socket that never opens fails via `onclose` and the normal backoff, so the watchdog cannot pile up connection attempts. The display's VPortal polling is started in `joinSession` (`connection.js`), not on reconnect, so a watchdog reconnect does not start it again; a new display join stops the previous poller first.
- On reconnect, sends `join` with `reconnect_token` from `sessionStorage` if one is stored.
- Server returns a new `reconnect_token` in `join_success`; stored in `sessionStorage.iv_session`.
- `join_error: "Role already taken"` with a stored token means the token no longer matches (a matching token always takes the slot). It is retried silently for up to 25 s from the first rejection in a row (`roleTakeover.js`); after that the position counts as taken by another device: `returnToRoleSelection()` (socket closed, token dropped, `iv_session` back to `{code}`) with an inline notice naming the position. A `join_success` resets the streak. Applies to the reconnecting screen after a reload and to a judge screen that lost its connection.
  *Why retry at all:* if `join_success` with the new token is lost on a connection that dies, the server still counts that dead connection as connected until the heartbeat closes it (≤ ~20 s: 15 s without pong, swept every 5 s) and rejects the retry with the old token. *Why the client decides, not the server:* both cases are a token mismatch, so the server cannot tell them apart either. *Why 25 s:* the ~20 s worst case plus margin; the limit is checked on each rejection, it adds no wait.

### i18n

Both locale files (`en.json`, `de.json`) are fetched in parallel at startup. `t(key)` resolves dotted key paths (e.g. `"reasons.squat.red.depth"`), falling back to English if a key is missing. Translated text is always bound with `x-text`, never `x-html`; a link inside a sentence (the rulebook link in the demo guide) is an `<a>` in the template whose text, and the parts of the sentence around it, are separate keys. Reactivity is driven by a dummy `_v` counter in an Alpine store: `setLanguage()` increments it, forcing every `t()` call in the template to re-evaluate. Language resolution order: `localStorage` → `navigator.language` prefix → `'en'`.

*Why the dummy `_v` counter:* Alpine's reactivity is property-access-based — a template re-evaluates only when the reactive properties it reads inside the expression change. `t()` resolves the key against a module-level `locales` object, so by default no Alpine-tracked property is read and changing the language wouldn't trigger any re-render. The workaround: `t()` itself touches `Alpine.store('i18n')._v` on every call (`void store._v` in `i18n.js`), so each invocation registers `_v` as a dependency of whatever effect ran it. `setLanguage()` bumps `_v`, which invalidates every effect that has called `t()`. Cost: a single counter bump re-evaluates every translated binding on the page — cheap because Alpine's binding count is small.

Reason keys in `constants.js` are i18n keys. They double as the identifier sent over WebSocket and the translation lookup key — adding a reason means one entry in `constants.js` and one entry in each locale file; no backend change required.

### Demo mode

`launchDemo()` creates a real session via `POST /api/sessions`, then opens 4 browser windows with `?code=XXXX&demo=<role>` params. `init.js` reads those params before Alpine boots and hands them to `app.js` on `alpine:init`; the connection's `start()` auto-joins the specified role. Requires the browser to allow pop-ups: `launchDemo()` checks every `window.open` result — `null`, or a window that is already `closed` (blockers that open and immediately close), counts as blocked. If any window is blocked the guide shows a hint instead of "Demo running" (all blocked: allow pop-ups and relaunch; some blocked: additionally, switch screens via "DEMO" in an open window); windows that did open stay open. There is no delayed re-check, so a blocker that closes a window later goes unnoticed. **Why** no delay: the check must not slow the launch, and the fallback via "DEMO" covers the rest.

Demo windows (`session.isDemo`) show "DEMO" instead of the session code (judge) or session name (display); clicking it opens role-select like the code link, which still shows the real code and QR code for a second device. The session behind it has a normal unique code, so several demos can run in parallel. `isDemo` is kept in `iv_session` (`demo: true`) and restored on reload, because `app.js` scrubs the URL params at startup. **Why** "DEMO" instead of the code: a demo window must not be mistaken for a real session.

### Display settings overlay

The display screen has a single interactive control: a low-contrast gear icon (top-left) and `S` keyboard shortcut, both of which open a small overlay with the pause form (see *Pause*), an "Edit layout" button (see *Display layout*) and a contrast-mode switch, and a "?" that explains the panel (see *In-place explanations*).

The contrast-mode switch (On/Off, `aria-pressed`) toggles the class `display-contrast` on the display root and persists as `iron-verdict:display-contrast`. All its rules live in `display-contrast.css` and are scoped under `.display-full.display-contrast`, so without the class the display is unchanged: solid light colours with a thick border (an unlit light keeps a visible ring), pure white bold texts (session tag, timer, waiting text, reasons, VPortal corners), filled verdict stamps; every text reaches at least 7:1 (WCAG AAA) against the black background, checked by `test_display_contrast.py`. *Why the background stays black:* the lights glow best on black on most screens; bright halls wash out dim greys and gradients, not the black itself. *Why on/off instead of a slider:* one click under time pressure, no fine-tuning at the venue. The mode is a device setting of its own, independent of the layout.

*Why a low-contrast gear plus a keyboard shortcut:* the display is mixed-deployment — sometimes the operator knows the app, sometimes a volunteer is at the keyboard. A faint gear is invisible at projector distance but discoverable on the operator laptop; `S` exists as the power-user path. There is no other interactive control on the display screen, so a single conventional dismiss model (`Escape`, click-outside) suffices.

*Why per-browser localStorage:* the same laptop typically goes to the same venue, so the settings should outlive a session; screen sizes and light conditions differ per screen, so layout and contrast are per device too. A new laptop re-tunes once. Server-side per-session storage would add a new API surface for a per-device UI preference — out of proportion with the value.

### In-place explanations

Three "?" buttons open a full explanation right where the question comes up (#159, #160), with no link to another page: in the display settings panel (the panel itself: opening it, pause, layout editor, layout code, contrast mode), beside "Stream overlay (OBS)" on role-select (the OBS setup, formerly `docs/obs-overlay.md`) and in the VPortal connect dialog (the connection to the competition software). The texts are structured locale entries (`help.display` / `help.obs` / `help.vportal`: a title and sections of `title` + `items`), rendered with `x-for` and `x-text` only — no HTML from the locales. Open state is UI state of the screen component (`displayHelpOpen`, `overlayHelpOpen`), for the dialog `helpOpen` in the vportal store, because the dialog belongs to no screen.

- **Display:** the box sits beside the panel (below it on narrow screens) but inside the panel's element, so `@click.outside` does not close the panel when it is clicked; it closes whenever the panel closes and starts closed the next time. It is therefore never on the free display or in the stream overlay unless the panel is open. The layout editor toolbar keeps its own hint and has no "?".
- **Role-select:** the "?" opens the OBS guide below the button, independent of the URL box; leaving role-select closes it.
- **VPortal dialog:** the "?" sits in the dialog's title row, so it is there in every step (federation, credentials, stage, connected); the text opens below the title and scrolls on its own, so the step's fields and buttons stay on screen. Every close path only sets `modalOpen = false`; `openModal()` resets `helpOpen`, so the text is hidden with the dialog and starts closed the next time. In the stream overlay the dialog — and the text, while open — is in the picture like the rest of the dialog; the text says so.
- No help elements on the judge screen.

*Why in the app instead of a docs page:* operators look for help on the device in front of them, often under time pressure and without access to the repository; one text in two languages is maintained in one place.

### Display layout

From the settings overlay the operator opens an edit mode (#106) to arrange the display for its screen: hall monitor, portrait screen, projector, stream. The blocks are the timer, the lights, the cards + reasons under the lights, the verdict, the VPortal lifter info and the VPortal attempt info. Session name and connection dot, the gear and the VPortal disconnected banner stay fixed and always visible (in the stream overlay only on a connection problem, see *Stream overlay*).

- **Model** (`displayLayout.js`): `{v: 1, blocks}`. A free block has `x`/`y` (percent of the display), `s` (scale 0.3–3) and `hidden`. `y` is the top edge, `x` the block's anchor (`BLOCK_ANCHORS`): the left edge for the lifter, the right edge for the attempt, the centre for timer, lights and verdict — the side the content grows from in the default layout. The lights also have `gap`: the gap between the three lights as a factor on the default `8rem` (0.4–2; a layout or code from before #154 without it gets 1). The cards block has only `gap` (extra distance to the lights, in light sizes, 0–2) and `hidden`: it stays under its light and scales with the lights. Positions snap to 1 %, scale and gap to 0.05. A stored or imported layout passes `sanitizeLayout`, which keeps only numbers (clamped) and booleans of a complete layout, so it cannot inject CSS; anything else counts as "no layout".
- **Rendering:** no layout → no class, the default flow layout of `layout.css` exactly as before. With a layout the root gets `display-layout-custom`; every block (`data-layout-block`) is absolutely positioned by an inline object `:style` (`left`, `top`, `transform: translateX(0 | -50% | -100%)` for its anchor, `--display-zoom`; the lights also `--orb-card-gap` and `--lights-gap`, which `layout.css` turns into `--orb-reason-gap`, the column gap and the room a reason may take from its neighbours). Every display size already multiplies through `--display-zoom`, so a block's scale is that variable set on the block. Hidden blocks are `display: none` (lights: `visibility: hidden`, so the cards keep their place). The layout is read from `localStorage` in the component's `init`, before the display is first shown — no jump on reload; a reconnect does not touch it.
- **Editing** (`screens/displayLayoutEditor.js`): the draft starts as a copy of the saved layout, or `null` for the default; the first drag or hide measures where the blocks are (`layoutFromRects`), so leaving the flow layout moves nothing. Pointer events (mouse and touch, `touch-action: none`, pointer capture on the grabbed element, move/up/cancel/lost capture handled on the root) move a block, the corner handle scales it around its anchor (the attempt's handle sits bottom-left), the cards frame changes the gap, the handle on the side of the lights their gap (the lights are centred, so the handle moves by as much as the gap changes). Hidden blocks show faded so they can be switched on again; the VPortal blocks show faded sample text, labelled as a sample, while VPortal delivers no lifter (the real lifter replaces it as soon as polling brings one). "Save" stores the draft (`null` → removes the key); if the browser cannot store it (blocked or full), the editor stays open with a message instead of pretending, "Cancel" or leaving the display drops it, "Reset" sets the draft back to the default. The export code is `IV1.` + base64url of the layout JSON; an imported code fills the draft, it is stored only with "Save".
- The editor only reads and writes component state: stores, connection, timer and VPortal polling run on unchanged while editing.

*Why per block instead of the former global zoom (0.7–1.5×):* screens differ in shape, not only in size — a portrait screen or a stream overlay needs a different arrangement. The zoom is replaced by the block scale, so there is one way to size things (maintainer decision on #106).
*Why anchors instead of top-left corners:* a block's width changes with its content (lifter name, decimal weight, "Good Lift" vs "No Lift"); anchored at the side it grows from, the attempt's weight can never be pushed off the right edge and the verdict stays centred.
*Why the lights gap stops at 0.4×:* the gap is also the room a reason may reach into the neighbouring column; below 0.4× the reason panels of neighbouring lights touch and long German reasons break inside a word at large scales (comparison matrix over a stream picture, maintainer decision on #154). Line breaks and reason font size stay as before. *Why a factor on `8rem` and not light sizes:* a missing value means factor 1, so every older layout and code keeps exactly today's gap.

*Why a coupled cards block:* moving cards freely could put a card under the wrong light; the useful freedom is the distance to the lights.
*Why the verdict sits 48 px lower in the default layout:* the editor labels have a fixed size (they do not scale with the display), the verdict label sits above the verdict and the cards label under the cards frame, so with the flow gap of 12 px they covered each other (#162). `display-layout.css` gives the verdict `margin-top: 48px` with an equal negative bottom margin, so the flow keeps its height and only the verdict moves — timer and lights stay put. The editor toolbar is flat and centred by auto margins (not `left: 50%`, which wraps it at half the screen width) and the attempt label grows to the left, so at 1280×720 no label or hide button is covered or off screen; `test_display_layout.py` checks this in English and German.
*Why only the toolbar ends the edit mode (not `S` / `Esc`):* a stray key under time pressure must neither drop nor save an arrangement.
*Why an export code instead of server storage:* layouts are per screen; the code copies one to a second device without a new API surface. An OBS browser source keeps its own layout like any display (see *Stream overlay*).

### Pause

A display operator starts a pause for the whole session from the settings panel (#163): by minutes (1–720; the displays count down) or until a time of day (the displays show "until HH:MM"), optionally with the next lift type (shown only; the head judge's lift type is unchanged). While it runs every display of the session, the stream overlay included, shows the pause big in the middle instead of timer, lights, verdict and VPortal lifter/attempt (`paused()`; VPortal polling continues; not while the layout editor is open). *Why not a layout block:* a fixed place in the middle is enough for "until 13:15"; a movable block needed a second editor view (maintainer decision on #163). It ends when its time is up (server task, see *Background work*), when the head judge starts the timer (`timer_start` first broadcasts `pause_update` `null`) or with "End break" on any display; then the displays show the real state again, e.g. a result that was not advanced yet.

- **End time:** stored as an absolute time (epoch seconds) and enforced by the server. Minutes are added to the server clock. For "until" the display converts today's time with its own clock (`endOfTimeToday`); the server only rejects an end not in the future (`past`) or more than 12 h ahead (`too_long`; past midnight only by minutes). *Why the device clock for "until":* devices set their clock automatically, and a minute off is no problem for a break display — not worth a time-zone protocol (maintainer decision on #163). *Why 12 h:* a typo (13:00 instead of 14:00) would otherwise give an almost 24-hour pause.
- **Countdown:** every `pause_update` and `join_success` carries `server_now_ms`; the store keeps the offset to the device clock, so all displays show the same countdown, and refreshes the remaining time every `PAUSE_TICK_MS` (250 ms, a display refresh, not a delay). At 0:00 the display waits for the server's end. "until HH:MM" is the end in the display's local time.
- **Nothing dropped silently:** the panel sends only with an open connection (otherwise the buttons are disabled and a note says so), shows "Sending…" until `pause_update` or `pause_rejected` arrives, and shows the rejection. A `join_success` after a reload or reconnect replaces the pause state and clears a pending request. The panel closes when the server confirms this display's request.

### Stream overlay

The display as an OBS browser source over the camera picture (#107; the OBS setup guide is the "?" beside the button, see *In-place explanations*). `/?session=CODE&overlay=1[&layout=IV1…]` is a fixed URL that opens the display of the session without a click; role-select offers it to copy ("Stream overlay (OBS)"; clipboard API on HTTPS, else the URL is selected).

- **Start:** `init.js` reads the params, sets `display-overlay` on `<html>` and hands them to `app.js`, which leaves the URL as it is; the connection's `startOverlay` sets `session.overlay`, puts the screen on *display* and calls `joinSession('display')` — the same join as the hall display (counts against `DISPLAY_CAP`, VPortal overlay started, reconnect by `websocket.js`). It takes precedence over a session stored in `sessionStorage`. No landing, role-select or *reconnecting* screen and no history entry: `join_success` finds the screen already on *display*.
- **Look:** `display-overlay.css`, scoped under `html.display-overlay`: transparent `html`, `body`, boot screen and display root (also in contrast mode), no decorative lines, no "Waiting…" text. Timer, reasons, verdict and the VPortal corners sit on a translucent dark panel (`--overlay-panel-bg`) with white, bolder text, so they read on any camera picture; the panel grows by a `box-shadow` spread (timer: `clip-path` against its negative bottom margin) instead of padding, so no block changes height and the lights never move. The lights stay without a panel. The markup hides the gear and the session name; the session tag with its dot appears only while the connection is not `connected` or the server announced a restart. `S` still opens the panel (OBS: "Interact"). While editing a layout the root shows a dark checkerboard, so white texts stay visible in a normal browser.
- **Layout:** stored under `iron-verdict:display-layout:overlay`, so a browser that is also a hall display keeps both. A valid `&layout=` code is the only source: the panel shows "Layout comes from the URL" instead of the edit button. An invalid code falls back to the stored layout with a hint in the panel.
- **VPortal:** polling needs a VPortal login on the device, and the overlay never passes role-select, so its panel (VPortal sessions only) opens the connect dialog. The dialog bumps `vportal.loginChanges` on connect/disconnect; the display screen watches it and calls `conn.restartDisplayOverlay()` (only while on the display), which restarts the VPortal overlay with the new login (not after the session ended). After a reload the stored login shows as connected, as on every device (see *Connect button after a reload* under *VPortal integration*). The button needs `kind === 'vportal'`, which the overlay learns only from the display start's session lookup (it skips role-select); with `streamOverlay` that lookup is retried at the polling interval until it succeeds, also without a login and without the disconnected banner. The disconnected banner itself shows in the stream, so its text points to "S" there (`vportal.disconnectedBannerOverlay`) instead of to role-select, which the overlay does not have (#173).
- **No session:** `session_ended`, and a final `join_error` (session not found, display cap), close the socket and stop the VPortal overlay like on the hall display, but `failOverlay` shows a short notice ("Session ended", "Session not found", "Join failed: …") on the transparent page instead of an alert and the landing screen. An invalid code in the URL shows the notice without connecting.

*Why the URL stays:* OBS reloads browser sources now and then (and on every start); the reload must open the overlay of the same session again. *Why `<html>` and `init.js`:* the boot screen comes before Alpine; a reload in OBS must not flash a dark full screen over the stream. *Why no alert:* a modal dialog in an OBS browser source blocks the page, and nobody sees it. *Why a panel and not only a text shadow:* a camera picture can be bright and busy anywhere; only a solid backdrop keeps grey and white text readable (maintainer decision on #107). *Why the dot only on a problem:* viewers should see a clean overlay; a lost connection still becomes visible (no silent state). *Why the session code in the URL is acceptable:* it is already in the role-select QR code; the OBS URL lives on the streaming PC and never appears in the stream. *Why the layout from the URL locks the editor:* otherwise an edit saved in OBS would silently disappear on the next reload.

### Lights and cards

A light shows only the verdict of one judge: white (valid) or red (invalid). The colour the judge picked for an invalid vote (red, blue, yellow) is shown as a card under the red light — display 40 % × 20 % of the light (scales with it and the lights block's scale), judge results panel 50 % × 25 %. Vote, protocol and server keep the four colours; only the rendering maps them (`voteLight.js`). The card is shown regardless of "Show reasons on display", which hides only the text.
*Why white/red plus card:* the classic referee-light convention; four light colours confused spectators (#115).

**Lights never move on the display.** The display content is vertically centred, so any height change would shift the lights. Therefore the card is always in the layout (`visibility: hidden` without a card), each light's column reserves light + card + two reason lines (`min-height` on `.display-orb-wrap`, which also sets `--orb-size` for the light), and "Waiting for judges…" shares one grid cell with the verdict stamp (they never show together; the stamp is always in the layout, hidden while idle). A reason longer than two lines still grows the column.
*Why so tight:* the reserved space had to fit the screen height at the former largest zoom (1.5) on 1280×720, 1366×768 and 1920×1080; the default layout keeps that spacing — hence the small padding/gaps of `.display-full` and the timer's negative bottom margin, which trims the empty descender space under its digits. `test_red_light_card.py` checks this.

### Reasons under the lights

The reason text sits centred under its light (display and judge results panel), centred by the column flexbox: at least light-wide (judge panel: up to 144 px), as wide as its longest whole word, and at most half the column gap into the neighbour's side. A word wider than that breaks at its soft hyphens (U+00AD), which `locales/de.json` sets by hand at the compound joints of long German reason words (`Hantel\u00adständern`); the browser shows a hyphen only where it actually breaks. Soft hyphens are break points for the box's `min-content` too, so an invisible, unhyphenated copy of the reason (`::after` with `content: attr(data-reason)`, `hyphens: none`) sizes the box to the longest *whole* word — otherwise words that fit would be split. Within multi-line reasons the browser still fills lines greedily and may use a soft hyphen there ("mit Hantel-" / "ständern"), as in normal German typesetting. Only a word without a fitting soft hyphen breaks anywhere, without a hyphen — the last-resort safety net. On the display each light's column is exactly as wide as the light, so the lights stay put when reasons appear, and the reason font scales with `vmin` and `--display-zoom` (the lights block's scale) like the lights. In the judge panel the columns split the panel width and the reason font shrinks a little on phones (16 px at 320 px width, 1.29rem from tablet width up).

*Why soft hyphens instead of `hyphens: auto` or a bundled hyphenation library:* Chrome on Windows/Linux downloads hyphenation dictionaries on demand — an external runtime dependency that venue Wi-Fi may block, so automatic hyphenation would silently differ between devices. A bundled library (patterns + WASM, ~100 KB, async) would add load time and an async first render for a fixed catalog of a few dozen reasons. Soft hyphens are deterministic on every browser and cost nothing at runtime; a new long reason without one is caught by `test_reason_centering.py`.

### Security note

The display screen shows `sessionName` but not `sessionCode` — deliberate, to prevent the code from being visible on a projected screen that anyone in the room could copy.
